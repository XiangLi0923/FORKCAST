# FORKCAST（食序）V0.3 产品需求文档

**范围。** 本文按 M0 r1 规范、实现及验收结果回写。比赛交付为本地 C+B Web 与 MCP 接口，全部使用模拟数据。早期六处食堂是设计构想，实际演示只使用已登记模拟场所。真实支付、预约、消费记录接入和生产上线不在赛期。

## 1. 用户、目标和主流程

| 用户 | 任务和目标 |
| --- | --- |
| 学生 | 在预算、时间与供应约束下获得一个可执行的午餐方案。有权调整、拒绝和坚持原有可行偏好。 |
| 运营者 | 在下一供餐窗开启前观察授权需求，查看缺口和资源限制，明确批准可执行备餐建议。 |

主流程为学生推荐、主动选择与可选分享、B 端授权聚合、运营审批、下一供餐窗生效与 C 端再次推荐。

## 2. 学生端

| 编号 | 功能 | 验收条件 |
| --- | --- | --- |
| C1 | 默认与筛选推荐 | 匿名进入可直接得到首选。明确预算、可用时间、食材与过敏限制为硬约束，营业和供给也参与校验。 |
| C2 | 调整和解释 | 支持赶时间、控预算、想换口味、指名与轻量条件。显示食堂、完整餐次、价格、时间区间、可用份数、理由、风险。匹配分与可信度分开。 |
| C3 | 动态重规划 | 售罄或窗变化后用新快照重算，保留原意向并提示主动重选。无可行供给时说明原因。 |
| C4 | 明确选择与反馈 | 想吃、打算吃、本人自报吃了或没吃分别记。曝光、浏览与自动重算不写意向。 |
| C5 | 分享治理 | 默认关闭分享。只有加入演示并主动授权后的声明进入当前 B 端聚合。撤回排除旧贡献，重新授权后仅纳入新声明。 |

## 3. 运营端

| 编号 | 功能 | 验收条件 |
| --- | --- | --- |
| B1 | 合规汇总 | OPS 按获授权的场所、供餐窗、菜品查看。偏好 P、意向 I、用餐自报 A 分别计算，至少 3 个不同授权会话才披露该渠道。未披露不视为零。 |
| B2 | 生成建议 | 对可见项取 max(I, A, floor(P/2)) 作为需求代理，减已计划供给得到非负缺口。追加建议受缺口、菜品供给配额、食堂产能及原料余量约束。均未披露时不生成提案。 |
| B3 | 人工确认 | 必须输入批准量并明确确认。服务复核场所权限、当前快照、提案版本和幂等键后，预留资源并记录确认审计。 |
| B4 | 下窗生效和读回 | 下一供餐窗生效才发布新可售量。支持读回确认和生效审计及对应历史快照。 |
| B5 | 失联与冲突 | 服务不可达时暂停写入并标注旧状态。快照、需求或计划冲突时重新生成和复核。 |

## 4. 决策与数据

R01 区分硬约束和软偏好。R02 按情境对口味、时间、价格、探索和营养参考评分。R03 以已登记完整餐次为决策单位。R04 在近似等优内考虑排队，备选保持多样。R05 解释冲突并动态重规划。R06 用关键事实的可信度独立标示不确定性。明确饮食限制所需证据不足时阻断候选，营养与排队均按模拟估算披露。

Web 走本机 HTTP，MCP 走本地 stdio，复用相同服务。EXTERNAL_AGENT、STUDENT、OPS 的权限由服务端识别。MCP 写工具需要人工通过同源 Web 签发的回执，默认 120 秒，绑定主体、运行、工具、动作和幂等键。首次成功消费，合法同键重试可回放。网页 HTTP 确认独立执行人工批准与权限校验。学生未经授权的细节不进入 B 端。

## 5. 验收与后续指标

| 验收 | 目标和现状 |
| --- | --- |
| E01 双端闭环 | 烤鸭售罄改荐鸡腿；批准路径 W2 烤鸭库存 3 并回荐烤鸭；未批准路径库存 0。源码包独立复验通过。 |
| 授权治理 | 意向 5，经授权选餐变 6，撤回后回到 5。小样本屏蔽。HTTP 复验通过。 |
| E03 MCP | 角色、同源回执、跨端状态读回及错误处理通过程序验证。 |
| GATE 2 | 经校验官方 wheel 在 Windows 空环境离线安装通过。 |
| GATE 1 | 可见 Edge 人工回执、同运行首次 MCP 成功、同快照读回和四张截图，仍 BLOCKED。 |

上线后可测量选择耗时中位数、首选采纳率、售罄重规划接受率、运营建议采纳和生效耗时。当前没有量化真实满意度、浪费或销量提升。
